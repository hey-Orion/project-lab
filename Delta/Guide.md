## Structure

**Pick one project per day** — don't split attention across both in the same session. Alternate days (SQL set one day, Order Pipeline the next) or run SQL set for a week first since it's your more foundational weak zone, then move to the integration project.

**Session shape (repeat daily):**
1. **Study (5-10 min)** — only on Day 1 of that project, or if you're totally stuck. After that, skip straight to step 2.
2. **Close the file completely.** Don't keep it open "just in case."
3. **Attempt the full rebuild from memory**, talking out loud as you go.
4. **When you get stuck**, note *exactly* where (which line, which concept) — then peek only at that specific part, not the whole file.
5. **Finish the attempt**, then compare your version against the reference line by line.
6. **Log your peek count** — even a simple tally (Day 1: 6 peeks, Day 2: 4, Day 3: 1...) turns this into visible progress instead of a vague feeling.

## Order to tackle things

1. **SQL set first** (Q1→Q8, in order) — it's shorter, and CTEs/window functions are your known weakest zone, so front-load them.
2. **Order Pipeline project second** — once SQL is trending toward zero peeks, move to the 5-tool integration project, since it depends on some of the same instincts (schema thinking) SQL builds.

## When to move on

- **Don't move to variations** until you've had **2-3 consecutive zero-peek rebuilds** in a row — one clean run could be luck.
- **Don't add new scope** (extra fields, new patterns) until the base version is genuinely cold — this is the exact trap that caused the "long code" overwhelm back on Day 6.

## Weekly check

Once a week, do one rebuild **fully timed**, like a real interview — this tells you not just "can I write it" but "can I write it under pressure," which is the actual bar that matters.

That's it — same core loop every day: close the file, attempt cold, peek only where stuck, compare, repeat. Consistency on this loop matters more than session length.
